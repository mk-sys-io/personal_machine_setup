# VPN Mitigation

## Philosophy

This is a multi-layered deny system designed to increase friction high enough
to make the user give up when attempting to install or use VPN software. It is
not designed to block every single path — it is designed to make casual VPN
usage impractical. A determined user can bypass any individual control.

## Threat Model

**Goal:** Prevent the user from installing and running VPN clients during
focused or locked mode.

**Assumption:** The user has physical access to the machine and sudo privileges
before locking. After `ark enable`, the root password is casked and the sudo
group is removed. Before `ark enable`, the user has full root access — this is
the window where pre-existing VPN artifacts must be caught.

**Scope:** VPN clients only — not VPN websites, not VPN configuration files,
not VPN browser extensions.

## Why VPN Websites Are NOT Blocked

Blocking VPN websites is security theater:

1. **VPN websites are marketing/download pages** — they are not service endpoints
2. **The real controls are:** package manager audit, sudo group removal, browser download policies
3. **DNS blocklist covers most download URLs** — but `curl | sh` scripts and alternative download methods exist
4. **Blocking websites creates maintenance burden** — VPN providers constantly create new domains
5. **The friction is in installation, not information** — knowing how to install a VPN is not the same as being able to

## Why VPN Websites ARE Included in Blocklist

Despite the above, VPN websites are included in `blocklist-custom.txt` for
these reasons:

1. **Defense in depth** — even if one layer is bypassed, others remain
2. **Eliminates casual browsing** — user cannot visit download pages to get installation instructions
3. **Consistency** — all distraction categories are blocked uniformly
4. **Low maintenance cost** — major VPN providers have stable domain names

## Architecture Overview

Six layers, each catching different delivery vectors. No single layer is
complete — the strength is in the overlap.

```
Layer 0: DNS Blocklist              — blocks VPN download URLs
Layer 1: Browser Policy Hardening   — extension/DoH/proxy/download
Layer 2: Enable-Time Artifact Gate  — VPN gate + package drift
Layer 3: Interface Block            — blocks tunnel interfaces
Layer 4: Sudo Removal               — prevents system installs
Layer 5: VPN Sites in Blocklist     — DNS-level domain blocking
```

## Layer 0: DNS Blocklist

The DNS blocklist prevents resolution of VPN provider websites, download
pages, and documentation. VPN domains are included in the "AI Web Apps" and
other categories of the blocklist generated by `blocklist-generate`.

This blocks:
- VPN provider websites (nordvpn.com, expressvpn.com, mullvad.com, etc.)
- VPN download pages
- VPN documentation and setup guides

**Limitation:** Does not block `curl | sh` scripts that pipe directly to
shell — these bypass DNS resolution of a download URL entirely.

---

## Layer 1: Browser Policy Hardening

Browser enterprise policies block VPN-relevant features: DNS-over-HTTPS
bypass, extension installation, proxy configuration, and (on Chrome) file
downloads.

**Chrome** (via `dotfiles/chrome/policy.json.template`):
- `DnsOverHttpsMode: "off"` + `BuiltInDnsClientEnabled: false` — forces system DNS
- `ExtensionInstallBlocklist: ["*"]` — blocks all extension installs
- `ProxyMode: "direct"` — prevents manual proxy configuration
- `DownloadRestrictions: 1` — catches .deb/.rpm/.appimage/.run downloads

---

## Layer 2: Enable-Time VPN Artifact Gate

When `ark enable` runs, it checks for VPN artifacts before locking down.
This catches VPN software installed during a prior unrestricted window.

### What It Checks

Four signal classes are scanned:

| Signal | Method | Examples |
|--------|--------|---------|
| dpkg packages | `dpkg-query -W` against a curated set | `wireguard-tools`, `openvpn`, `tailscale`, `nordvpn`, `mullvad-vpn`, `expressvpn`, `protonvpn`, `strongswan`, `openconnect` |
| Binaries | `shutil.which` + user directories (`~/.local/bin`, `~/go/bin`, `~/.cargo/bin`, `~/bin`) | `wg`, `openvpn`, `tailscale`, `ss-local`, `sing-box`, `xray`, `v2ray`, `tor`, `torsocks` |
| systemd units | `list-unit-files` + regex patterns | `wg-quick@*`, `openvpn@*`, `tailscaled`, `shadowsocks*`, `v2ray*`, `xray*`, `sing-box*`, `tor.service` |
| Stray files | Filename regex scan of `~/Downloads`, `~/bin`, `/opt/*` | `*vpn*`, `*wireguard*`, `*openvpn*`, `*.AppImage` with VPN-related substrings |

### What Happens When Something Is Found

Any finding produces a `PrereqError` listing each artifact with a remediation
command (e.g., `sudo apt purge wireguard-tools`, `rm ~/.local/bin/wg`).
`ark enable` refuses to proceed — fail-closed, same behavior as the package
manager audit.

### Package Drift Detection

The artifact gate catches known VPN packages, but what about packages
installed between enable/disable cycles? The package drift check extends
Layer 2 to catch any dpkg state change, not just known-bad packages.

**How it works:** A snapshot of the installed package list is captured at
both enable and disable time. On the next enable, the current package list
is compared against the baseline. Any added package triggers a
`PrereqError` — fail-closed, same UX as the VPN artifact gate.

The baseline is stored at `$ARK_DATA_PATH/baselines/installed-packages.txt`
(a sorted list, one package per line). It is overwritten atomically on each
capture — only the latest snapshot matters.

**Behavior:**
- Drift check runs **before** baseline capture — detect first, then snapshot
- `PrereqError` lists each added package with `sudo apt purge <pkg>` remediation
- Baseline captured at both enable and disable — next enable starts clean

## Layer 3: Interface Block

After lockdown, a VPN tunnel (tun/tap/wg interface) can operate silently.
The nftables firewall in focused mode is accept-all except direct `:53`
port 53 traffic — tunnels work. The correct response is to **block**
tunnel traffic, not detect it.

Two components work together:

**A: Enable-time gate** — Before locking, the system checks for active
tun/tap/wg interfaces. Detection is by interface **type**, not name (names
like `wg0`/`tun0` are trivially renamed):
- `/sys/class/net/*/tun_flags` file presence indicates a tun/tap device
- `ip -d -j link show type wireguard` identifies WireGuard interfaces

If any are active, `ark enable` refuses to proceed (fail-closed).

**B: nftables hard block** — Rules in `nftables.conf.restricted` drop all
traffic on tun/tap/wg interfaces. Applied at enable-time via
`firewall.apply()`. The tunnel interface may exist but carries no data —
it is dead.

- `tun*`/`tap*` — drops all traffic unconditionally
- `wg*` — drops WireGuard traffic **except** the netns subnet (`10.0.4.0/30`)
  and IPv6 loopback (`fd00::/128`), since the internet namespace uses veth,
  not wg

**Unrestricted mode:** These rules are not present — the base config has no
tunnel drops.

## Layer 4: Sudo Removal

After `ark enable`, the user is removed from the `sudo` group. This prevents:
- Installing `.deb`/`.rpm` packages (requires sudo)
- Modifying system paths (`/usr/bin`, `/usr/local/bin`)
- Changing file permissions on system binaries
- Loading AppArmor profiles
- Modifying kernel modules

### Limitation

The user can still:
- Run executables in their home directory
- Use `curl | sh` if the script doesn't require root
- Rename and execute binaries

These are mitigated by other layers (L2 artifact gate catches at next
enable, L1 browser policy restricts downloads).

---

## Layer 5: VPN Websites in Blocklist

VPN websites are included in `blocklist-custom.txt` for defense in depth,
consistency, and low maintenance cost. See "Why VPN Websites ARE Included
in Blocklist" above.

## VPN Binary Distribution Formats

### Research Summary

| VPN | Primary Method | File on Disk? | Blocked By |
|-----|---------------|---------------|------------|
| NordVPN | `curl \| sh` (official) | No | DNS blocklist, sudo removal |
| NordVPN | `.deb`/`.rpm` | Yes | Package manager audit, sudo removal |
| NordVPN | `.AppImage` (community) | Yes | L2 (artifact gate), L4 (sudo removal) |
| ExpressVPN | `.run` file | Yes | L2 (artifact gate), L4 (sudo removal) |
| ExpressVPN | `.deb` | Yes | Package manager audit, sudo removal |
| Mullvad | `.deb`/`.rpm` | Yes | Package manager audit, sudo removal |
| WireGuard | `.deb`/`.rpm` | Yes | Package manager audit, sudo removal |
| OpenVPN | `.deb`/`.rpm` | Yes | Package manager audit, sudo removal |

### Critical Gap: `curl | sh`

NordVPN's official installation method is
`curl -sSf https://downloads.nordvpn.com/linux/install.sh | sh`. This:
- Creates no file on disk
- Pipes directly to shell
- Executes immediately

**Mitigation:** DNS blocklist blocks `downloads.nordvpn.com`. If DNS block
is bypassed (e.g., hardcoded IP), the script still requires sudo to install
to `/usr/bin/`, which is removed.

### Critical Gap: `.run` Files

ExpressVPN distributes as a `.run` file (e.g.,
`expressvpn-linux-x86_64-3.3.0.run`). This requires execute permission
(which it has by default after download). Layer 2 catches the binary at
next enable; Layer 4 (sudo removal) blocks system install.

## Known Gaps (the residual)

What no combination of these 6 layers catches:

1. **Userspace proxies via generic tools**: `ssh -D` to a raw IP,
   `tor+torsocks`, `shadowsocks-local`, `sing-box` in system-proxy mode.
   No root, no tun interface, no file created. Egress is accept-all in
   restricted nftables. Requires egress allowlisting to close —
   disproportionate for the self-control threat model.

2. **curl | sh via raw IP**: If DNS is bypassed (hardcoded IP for
   NordVPN's CDN), the script runs and installs to user-space (no sudo
   needed for user-space binaries). `curl` itself is not blocked.
   Mitigated by: most VPN curl|sh scripts DO require sudo to install
   to `/usr/bin`.

3. **Pre-existing binary outside known patterns**: A VPN binary renamed
   to a non-matching name (e.g., `work` instead of `wg`). Detection by
   filename only; ELF-header scanning disproportionate for threat model.

**What these gaps mean:** The remaining attack surface requires deliberate
premeditation — staging binaries during unrestricted windows, configuring
manual proxies, or using raw-IP direct connections. This is consistent with
the "friction not wall" philosophy: the system prevents impulsive bypass;
deliberate circumvention requires leaving evidence in the user's own review
ritual (`ark status`).

## Verification

After enabling, verify each layer:

1. **DNS Blocklist (L0):** `nslookup nordvpn.com` should fail
2. **Browser Policy (L1):**
   - Brave: `chrome://policy` — verify `DnsOverHttpsMode: off`, `DownloadRestrictions: 1`
3. **Enable-Time Gate (L2):**
   - VPN artifacts: install `wireguard-tools`, then run `ark enable` — should refuse with remediation instructions
   - Package drift: `ark disable` → `sudo apt install sl` → `ark enable` → should refuse listing `sl`
4. **Interface Block (L3):**
   - Enable-time gate: `ip tuntap add mode tap test0` → `ark enable` should refuse
   - nftables block: after enable, `nft list ruleset` should show tun/tap/wg drop rules
   - Clean up: `ip tuntap del mode tap test0`
5. **Sudo Removal (L4):** `sudo -l` should fail
6. **VPN Blocklist (L5):** `getent hosts nordvpn.com` should fail
